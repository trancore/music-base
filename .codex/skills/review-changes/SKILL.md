# 変更をレビューする

リポジトリ固有の設計と規約を根拠に差分をレビューする。レビュー中はファイル、ステージ状態、コミットを変更しない。

## 1. リポジトリを理解する

差分を評価する前に、次を確認する。

- リポジトリルートと、対象ファイルに適用されるすべての `AGENTS.md`
- `git status --short --branch`、現在のブランチ、デフォルトまたはPRのベースブランチ
- README、アーキテクチャ文書、主要なマニフェスト、ロックファイル、解析・テスト設定
- ソース、テスト、ドキュメントのディレクトリ構成と、変更箇所に隣接する実装
- 変更に関係する外部APIやパッケージの仕様。現在の仕様確認が必要なら公式資料を優先する

確認結果から、言語、フレームワーク、状態管理、永続化、依存方向、サービス境界、プラットフォーム制約、検証コマンドを特定する。一般論よりリポジトリ内の明示的な設計を優先する。

## 2. レビュー単位を確認する

差分を読む前に、ユーザーへ必ず次のどちらでレビューするか確認する。すでに依頼文で指定されていても確認する。

- **commit単位**: ステージ済み差分だけを対象にする。
- **PR単位**: ベースブランチから現在の `HEAD` までのコミット済み差分だけを対象にする。

利用可能なら選択式の質問ツールを使い、利用できなければ短い質問で確認する。レビュー単位を推測して進めない。

### commit単位

- `git diff --cached --stat`、`git diff --cached --name-status`、`git diff --cached` で対象を確定する。
- ステージ済み差分が空なら、レビュー対象がないことを伝えて停止する。ユーザー自身によるステージを求め、代わりにステージしない。
- 未ステージ変更と未追跡ファイルを対象へ混ぜない。

### PR単位

- 明示されたベース、PRメタデータ、`origin/HEAD`、リポジトリ設定の順にベースブランチを特定する。複数候補が残る場合はユーザーへ確認する。
- ベースとのmerge-baseを求め、`git diff <merge-base>..HEAD` の統計、ファイル一覧、パッチを対象にする。
- ステージ済み、未ステージ、未追跡の変更を対象へ加えない。
- 使用したベース参照とmerge-baseをレビュー結果へ記載する。

## 3. 差分を検証する

パッチだけで判断せず、変更されたシンボルの呼び出し元、実装するインターフェース、関連テスト、関連ドキュメントを読む。生成ファイルは生成元との整合性を確認し、生成物だけの問題として重複報告しない。

変更によって新しく生じた、または悪化した問題だけを指摘する。各候補について再現経路、契約違反、失敗条件のいずれかを具体的に確認する。根拠のない推測、好みだけのスタイル指摘、変更範囲外の既存問題は指摘に含めない。

変更内容に応じた非破壊の検証を実行する。フォーマッターはチェックモードを使い、ファイルを書き換えない。関連テスト、静的解析、ビルド、ドキュメントビルドのうち実行したもの、失敗したもの、実行できなかったものと理由を記録する。

次の観点から、変更に関係するものだけを使用する。

- アーキテクチャ、依存方向、責務とサービス境界
- 正確性、ドメイン要件、状態遷移、エラー処理
- セキュリティ、秘密情報、ユーザーデータと破壊的操作
- プラットフォーム差異、外部I/O、障害からの復旧
- 性能、メモリ、並行処理、リソース上限
- テスト、ドキュメント、互換性、運用上の確認可能性

## 4. 指摘を報告する

指摘を観点別にグループ化し、各グループ内では重大度順に並べる。空のグループは出力しない。

重大度を次のように付ける。

- **P0**: データ損失、秘密情報漏えい、広範な停止など、直ちに修正すべき致命的問題
- **P1**: 通常の利用経路を壊す、またはリリースを妨げる高確率の問題
- **P2**: 特定条件で誤動作、回復不能、重大な性能劣化を起こす問題
- **P3**: 影響は限定的だが、今回の変更で修正する価値がある明確な問題

各指摘を次の形式にする。

```text
- [P1] 短いタイトル — path/to/file:line
  問題: 何が誤っているか
  影響: どの条件で何が起きるか
  根拠: 差分と周辺実装から確認した事実
  修正案: 最小限の修正方針
```

最初にレビュー単位と対象を示し、その後に指摘、検証結果、残存リスクの順で報告する。指摘がなければ `指摘なし` と明記し、検証できなかった事項だけを残存リスクとして示す。

## 5. コミット前に停止する

コミット依頼の一部として実行している場合、P0からP3まで1件でも指摘があれば `git commit` を実行しない。全指摘を提示した後、ユーザーへ次の判断を求めて停止する。

- 指摘を修正する
- 指摘を承知してコミットを続行する
- コミットを中止する

ユーザーが続行を明示するまでコミットしない。指摘がない場合はレビュー通過を明記し、後続のコミット処理へ引き継ぐ。レビュー単体の依頼では修正やコミットを自動実行しない。
