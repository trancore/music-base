# 変更をコミットする

## 概要

現在の作業ツリーから、レビューしやすい目的別のコミットを作成する。リポジトリの `AGENTS.md` に従い、無関係なユーザー変更を保持し、pushやPR作成は行わずに終了する。

## 手順

### 1. リポジトリを確認する

- 編集・コミット前に、適用される `AGENTS.md` を読む。
- `git status --short --branch`、`git diff` を実行し、対象になり得る未追跡ファイルも確認する。
- ベースブランチと、現在のブランチがデフォルトブランチかを確認する。
- 既存のユーザー変更をユーザーの所有物として扱う。`reset`、`clean`、破棄、上書きは行わない。

### 2. 対象範囲とコミット粒度を決める

- ユーザーの依頼で許可されたファイルだけを対象にする。
- 作業ツリーが混在している、または対象が曖昧な場合、`git add -A` を使わず、対象ファイルを確認する。
- ツールチェーン設定、CI、実装、テスト、ドキュメントなど、目的の異なる変更を別コミットに分ける。
- 各コミットは可能な範囲で自己完結させ、整形変更や無関係なリファクタリングを混ぜない。

### 3. ステージして確認する

- 明示的なパスを指定してステージする。1ファイル内に対象外の変更がある場合はパッチ単位でステージする。
- `git diff --cached` を確認してからコミットする。秘密情報、認証情報、生成物、ユーザーデータが含まれていないことを確認する。
- 利用できる関連検証を実行し、実行できない検証と理由も記録する。

### 4. コミットする

- リポジトリの慣例に従い、簡潔な命令形の件名を使う。通常は `<type>: <description>` 形式を優先する。
- 確認済みの論理単位ごとに1コミットを作成する。ユーザーが明示的に依頼しない限り、既存コミットのamend、rebase、履歴書き換えは行わない。
- このSkillではpush、PR作成、マージ、ブランチ削除を行わない。

### 5. 引き継ぐ

- `git status --short --branch` を再実行し、`git log --oneline` で新しいコミットIDを確認する。
- コミットしたファイル、未追跡・未コミットのまま残ったファイル、実行した検証を報告する。
- ユーザーがpushやPRも依頼している場合、コミット完了後に `$create-pull-request` へ引き継ぐ。
