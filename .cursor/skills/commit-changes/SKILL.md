# 変更をコミットする

## 概要

現在の作業ツリーから、レビューしやすい目的別のコミットを作成する。`AGENTS.md` と `.cursor/rules/project-agents.mdc` に従い、無関係なユーザー変更を保持し、push や PR 作成は行わない。

## 手順

### 1. リポジトリを確認する

- `AGENTS.md` を読む。
- `git status --short --branch`、`git diff` を実行し、未追跡ファイルも確認する。
- ベースブランチと、現在のブランチがデフォルトブランチかを確認する。
- 既存のユーザー変更を保持する。`reset`、`clean`、破棄、上書きは行わない。

### 2. 対象範囲とコミット粒度を決める

- ユーザーの依頼で許可されたファイルだけを対象にする。
- 作業ツリーが混在している、または対象が曖昧な場合、`git add -A` を使わず、対象ファイルを確認する。
- ツールチェーン設定、CI、実装、テスト、ドキュメントなど、目的の異なる変更を別コミットに分ける。
- 各コミットは可能な範囲で自己完結させ、整形変更や無関係なリファクタリングを混ぜない。

### 3. ステージして確認する

- 明示的なパスを指定してステージする。1 ファイル内に対象外の変更がある場合はパッチ単位でステージする。
- `git diff --cached` を確認してからコミットする。秘密情報、認証情報、生成物、ユーザーデータが含まれていないことを確認する。
- 利用できる関連検証を実行し、実行できない検証と理由も記録する。

### 4. コミットする

- リポジトリの慣例に従い、簡潔な命令形の件名を使う。通常は `<type>: <description>` 形式を優先する。
- 確認済みの論理単位ごとに 1 コミットを作成する。ユーザーが明示的に依頼しない限り、amend、rebase、履歴書き換えは行わない。
- コミットメッセージは HEREDOC で渡す。

```bash
git commit -m "$(cat <<'EOF'
<type>: <description>

EOF
)"
```

- この Skill では push、PR 作成、マージ、ブランチ削除を行わない。

### 5. 引き継ぐ

- `git status --short --branch` を再実行し、`git log --oneline` で新しいコミット ID を確認する。
- コミットしたファイル、未追跡・未コミットのまま残ったファイル、実行した検証を報告する。
- ユーザーが push や PR も依頼している場合、完了後に `create-pull-request` Skill へ引き継ぐ。

## コミット前レビュー

ユーザーがコミット依頼時にレビューを求めている、または変更が大きい場合は、先に `review-changes` Skill を実行する。
