# アーキテクチャ

アプリは、UI、状態管理、ドメインロジック、データアクセス、プラットフォーム固有処理を分離します。初期実装ではRiverpodを状態管理と依存注入に、go_routerを画面遷移に使用します。画面シェルはPCでは左サイドバーと上部固定の再生ドック、SPでは上部固定の再生ドックと下部ナビゲーションを表示し、幅700pxを境にレイアウトを切り替えます。画面遷移は短いFadeと水平Slideを共通適用します。

## ディレクトリ構成

- `lib/app/`: アプリ起動、Provider構成、テーマ、ルーティング
- `lib/domain/`: アプリ設定などのモデルと抽象インターフェース
- `lib/data/`: SharedPreferencesによる設定保存、ローカルディレクトリスキャン、音楽再生、DriftによるライブラリDB
- `lib/presentation/`: 画面とUIコンポーネント
- `lib/platform/`: Windowsなどプラットフォーム固有処理の境界

大きな画面は、公開するページWidgetを入口として、同じ機能ディレクトリ内の`part`ファイルへレスポンシブ表示、一覧、カード、ダイアログを分割します。ルーティング定義とアプリシェル、曲一覧とアルバム／アーティストのページング状態も別ファイルに分け、外部から参照するページ、Provider、Notifierの名前は入口ファイルで維持します。

ローカルファイルアクセス、SMBアクセス、音楽再生、MusicBrainz連携、タグ処理、CDリッピング、音声解析は独立したサービス境界として追加します。外部サービスのレスポンスやプラットフォームAPIを、そのままUIへ渡してはいけません。

## 永続化

設定はSharedPreferencesへ保存します。ライブラリ情報のキャッシュはDrift SQLiteデータベースへ保存し、音源パス、曲名、アーティスト、アルバム、ファイル指紋、最終確認日時を保持します。FTS5による検索、キーベースページング、画像のハッシュ重複排除と遅延読込により最大10万曲を全件メモリへ展開せず扱います。音源ファイル本体は保存せず、選択されたローカルディレクトリまたはSMB共有を正本として扱います。

`LibrarySourceStore`は選択中の参照先、最後に利用したローカル参照先、macOSのディレクトリアクセス復元、旧キャッシュの`source_key`補正を担当します。`LibraryRepository`実装は検索、ページング、スキャン結果のトランザクション反映を担当し、既存のSharedPreferencesキーとDriftスキーマを維持します。

ライブラリの再スキャンは非同期で実行し、UIの状態をローディングへ置き換えず、完了するまで直前のキャッシュページを保持します。成功後に一覧とグループを再取得し、失敗時はキャッシュを維持したまま復旧可能な警告として通知します。

アルバム別・アーティスト別の表示はSQLite上で集約し、グループ自体もキーベースページングします。グループ選択後の曲一覧と全曲再生は、同じ検索クエリへアルバムまたはアーティスト条件を追加して処理します。

FLACのディスク番号・トラック番号とメタデータ解析バージョンもキャッシュします。SMBスキャナーはFLACメタデータブロックのヘッダーを順にレンジ読み込みし、Vorbis Commentと2MB以下のPICTUREだけを取得します。解析バージョンが古いキャッシュは、ファイル指紋が同じでも次回スキャン時に再解析します。

ローカルディレクトリスキャナーはサブディレクトリを再帰的に走査し、FLACとMP3をライブラリ候補として扱います。ローカルスキャンでは`audio_metadata_reader`を通じてMP3のID3タグとFLACのVorbisコメント、2MB以下のアートワークを読み取り、タグがない場合はパスから推定したメタデータへフォールバックします。メタデータとアートワークはDriftのライブラリテーブルへキャッシュします。ファイル形式やタグの追加対応はスキャナーとメタデータサービスの境界内で行います。

音楽再生は`PlaybackService`の抽象インターフェースを通じて利用します。現在の実装はjust_audio、Windows実装、Darwinネイティブ実装を使用し、ファイルパスを音源として再生します。全曲再生の順序はSQLiteの一時キューへ保存し、現在位置の音源だけを解決します。UIは再生エンジンへ直接依存せず、サービスの状態を表示します。

`PlaybackAudioSourceResolver`はローカルファイルとSMBストリームの`AudioSource`生成、および有効なSMBストリームの破棄を担当します。デスクトップのリアルタイムスペクトル実装は、共通のEventChannelアダプターでPCMのバッファリングとスペクトル変換を行い、Windows／macOS固有クラスにはチャンネル名だけを残します。

インターネットラジオは`InternetRadioStation`と`RadioStationRepository`で局情報を管理します。局情報はSharedPreferencesへ保存し、再生時に`AudioSource.uri`へ変換します。WebページURLと音声ストリームURLは同一視せず、保存前にURL形式を検証し、just_audioで接続テストを行います。

Radio Browser検索は`RadioBrowserService`の境界で扱います。公式APIの`url_resolved`と`lastcheckok`を使用し、検索結果をアプリ内モデルへ変換してからUIへ渡します。APIリクエストには識別可能なUser-Agentを設定します。

音声解析は`AudioAnalysisService`の抽象インターフェースで扱います。ローカル音源は`audio_decoder`を通じて振幅データを取得し、SMB音源や解析失敗時は再生位置ベースのフォールバック表示を使います。UIは解析エンジンへ直接依存しません。実スペクトル解析を追加する場合は、このサービス境界へ別の実装を追加します。

周波数スペクトル計算は`calculateSpectrum`として純Dartのドメイン関数に分離しています。入力を1フレームあたり最大2048サンプル、出力を最大128バンドに制限し、Windows/AndroidのPCMアダプターから再利用できるようにしています。

Androidの`RealtimeSpectrumService`実装は、`just_audio`が公開するAndroid AudioSession IDをMethodChannelでネイティブの`android.media.audiofx.Visualizer`へ渡し、FFTコールバックをEventChannelでUIへ配信します。macOSではmacOS 14.2以降のScreenCaptureKitをこのアプリのプロセスだけに限定してPCMフレームを取得し、専用EventChannelでメモリ上だけFlutterへ渡します。ネイティブキャプチャを開始できない場合や権限を拒否した場合は通常のビジュアライザへフォールバックします。

Windowsの`RealtimeSpectrumService`実装は、Windows SDKのプロセスループバックでこのアプリと子プロセスが再生したPCMフレームだけを取得し、EventChannelでFlutterへ渡します。ほかのアプリやシステム全体の音は取得しません。Flutter側でフレームを`calculateSpectrum`へ入力します。録音ファイルとして保存せず、アプリ内メモリ上だけで処理します。

プレイリストとプレイリストフォルダは`PlaylistRepository`の抽象インターフェースを通じて保存します。SharedPreferencesには手動プレイリストの名前と音源パス、またはオートプレイリストの名前と検索条件に加え、配置先を示す`parentFolderId`と同階層の`sortOrder`を保存します。フォルダも同じ親参照と並び順を持つ独立したJSON一覧として保存し、再帰的なツリーを構成します。手動プレイリストは正規化パス索引を使って現在の音源キャッシュ全体へ解決し、オートプレイリストは保存した検索条件をDBへ直接適用します。どちらもライブラリ画面のページングや絞り込み状態には依存しません。`M3uPlaylistParser`はUTF-8のM3U／M3U8を、`MusicBeePlaylistParser`はMusicBee version 4のバイナリMBPをアプリ内のパス一覧へ変換し、ファイル選択とUI状態から分離しています。ルート変換は現在のキャッシュで実在を確認できた曲だけを候補とし、未解決パスは復旧できるよう保持します。旧形式の保存データは最上位の手動プレイリストとして読み込みます。音源ファイル本体はプレイリストへコピーしません。

MusicBrainz連携は`MusicBrainzService`を通じて利用します。APIクライアントはJSONレスポンスを`MusicBrainzRelease`へ変換し、識別可能なUser-Agent、1秒あたり1リクエスト以下の間隔制御、検索結果のメモリキャッシュを適用します。

SMB接続は`SmbService`の抽象インターフェースを通じて利用します。接続情報のうちホスト、共有名、サブフォルダ、ユーザー名は設定へ保存し、パスワードは`flutter_secure_storage`へ保存します。SMBスキャナーは接続テストとは別のサービス処理として共有内を再帰走査し、FLAC/MP3をライブラリDBへキャッシュします。SMB再生は`StreamAudioSource`のレンジ要求をSMBの部分読み込みへ変換し、音源本体をアプリへコピーせずに再生します。

参照先の切断、認証失敗、ファイル消失などは復旧可能なエラーとして扱い、UIやサービス全体をクラッシュさせない設計にします。

CD検出とリッピングはWindows固有機能です。`DefaultWindowsCapabilities`が対象プラットフォームを判定し、AndroidとmacOSではCD importメニューを表示せず、直接ルートへアクセスした場合も説明画面を表示します。Windows固有のCD処理を共有ドメインコードへ直接混在させません。

macOSのローカルディレクトリアクセスは、設定したパスとともにsecurity-scoped bookmarkを保存して維持します。Pickerで新しいフォルダを明示的に選択した場合は新しいbookmarkを先に保存してからスキャンし、再スキャン時は保存済みbookmarkとパスを検証します。Runnerにはユーザー選択フォルダの読み書きとネットワーククライアントのSandbox entitlementを設定し、SMB認証情報は従来どおりプラットフォームの安全な資格情報ストレージへ保存します。

CD取り込みの出力計画は`CdImportPlanner`で作成します。MusicBrainz releaseの総トラック数と物理CDのトラック数を検証したうえで、選択された一部の曲を曲順に対応付け、FLAC／MP3の拡張子、タグ候補、出力パスを組み立てます。既存パスの上書きは計画段階で拒否し、実ドライブの読み取りとエンコードはWindows固有のサービスから呼び出します。

WindowsのCDドライブ検出は`CdDriveService`の境界で扱います。Windows実装はPowerShellから`Win32_CDROMDrive`のドライブ文字、デバイス名、メディア挿入状態を取得します。Androidや非Windows環境では利用可能性をエラーとして返します。

CDトラック一覧は`CdTrackService`で扱い、Windows実装はCD AudioのMCI APIからトラック数と長さを取得します。MCI呼び出しとPowerShell実行はWindowsデータ層に閉じ込め、共有層は`CdTrack`モデルだけを受け取ります。

音声データの取り込みは`CdRippingService`で扱います。Windows実装は外部`ffmpeg.exe`へCDドライブ、トラック番号、FLAC／MP3 codecを渡し、`-n`と事前存在確認で上書きを防止します。`CdRippingCancellationToken`により実行中のプロセスを停止できます。ffmpeg未導入や実行失敗は通常の復旧可能なエラーとして扱います。

取り込みが正常に完了した後、出力先が設定済みのローカルライブラリ配下であれば、`CdDrivePage`がライブラリを再スキャンします。SMB参照先や設定済みライブラリ外の出力先は自動変更しません。
